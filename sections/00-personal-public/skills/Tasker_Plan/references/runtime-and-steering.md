# Status Updates and Steering

Read this reference when meaningful progress or a user correction requires the written plan to be updated.

## Keep status meaningful

Use the status already established by the project. Common useful states include planned, active, blocked, and completed. Describe what the current status means instead of introducing additional process.

Update the plan when a task begins, finishes, changes direction, becomes blocked, or gains evidence that clears a blocker. Keep completed work, remaining actions, and the next step distinguishable.

Keep the numbered plan in its group's `backlog/`, `active/`, or `completed/` directory matching its verified status. Keep planned or queued work in `backlog/`; keep active or blocked work in `active/` and record the exact blocker. When work the user has permitted changes that status, move the same plan to the matching directory inside its group. Preserve its filename, number, frontmatter, work log, and history; update the owner index, epic state, and affected plan links in the same maintenance pass. Use `archived/` only for actual archival.

For each material transition, append a dated entry supported by evidence to the numbered plan's `Work Log`. Update its `Artifacts`, `Decisions`, `Validation`, blockers, and unfinished work in the same maintenance pass when the event affects them. Keep the epic's `EXEC_STATE.md` synchronized with verified external artifacts without replacing the numbered plan's history.

## Apply user direction

Record a correction when it changes the plan's accepted scope, priority, completion criteria, assumptions, or next action. Update the affected sections together, append the change to `Work Log`, and preserve unaffected work and earlier decisions.

Name excluded work. Do not treat a new preference or priority as permission to expand the task, contact other people, or alter unrelated files.

## Update the document only when the user allows it

If the user forbids plan updates, leave the document unchanged. Report the verified current state and, when useful, describe the proposed update.

Use an available project or runtime tool only when the work calls for it and the user has permitted it. The planning skill does not require a particular tool, runtime goal, workflow, owner, or reporting mechanism.
