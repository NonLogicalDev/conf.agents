## Visible thread titles

- Name a visible continuing thread from the work it actually owns. This naming rule does not create a thread, choose a machine, move work, or assign an owner; make those decisions separately with the available runtime tools and the user's actual permission.
- Use `Task[<identity>] :: <description> :: <YYYY-MM-DD>` for one issue or project task, `Owner[<identity>] :: <description> :: <YYYY-MM-DD>` for a continuing owner responsible for several tasks and their combined result, `Oracle[<identity>] :: <YYYY-MM-DD>` for an entity with deep expertise in a project that can speak on its behalf, and `Auto[<name>] :: <description> :: <YYYY-MM-DD>` for an automation the user requested or started.
- Use `#<ticket>` only when the thread actually delivers that ticket or owns that epic. Otherwise use `$/<project-area>` with the user's established project name. A passing ticket mention, branch, working directory, host, or creation mechanism does not choose the identity.
- Use `Owner[...]` only when the thread coordinates several tasks and checks their combined result. One helper, one issue, or the word “owner” in a plan does not turn a `Task[...]` into an owner. Use `Auto[...]` only for an automation the user actually requested or started; a schedule or temporary helper does not create an automation thread.
- Use `Oracle[...]` for established project expertise and representation: explaining the project's design, history, decisions, and current state on its behalf. This role does not require coordinating delivery tasks. Oracle titles omit the description. Use the project's established `$/<project-area>` identity, for example `Oracle[$/leafnote] :: 2027-04-03`.
- For Task, Owner, and Auto titles, keep the description short and specific, usually three to eight words. Do not include the host, branch, checkout, home directory, duplicate date, literal `<...>` placeholder, retired category prefix, or generated temporary title.
- Use the thread's real creation date in the user's configured timezone and preserve it across ticket, role, description, or project changes. Read actual thread metadata when the date is missing; use older evidence only when it establishes the date and say when it is inferred. Do not guess today.
- When identity or role changes, rename the same thread and preserve its ID, original date, owner, host, goal, and useful history. For example, a task can move from `Task[$/leafnote] :: Replace offline search index :: 2027-04-03` to `Task[#APP-77] :: Replace offline search index :: 2027-04-03`, then to `Owner[#EPIC-12] :: Coordinate offline search migration :: 2027-04-03` only when it truly becomes the continuing owner. Do not create a replacement thread to make naming tidier.
- Preserve an established `Auto[...]` name and original date. Do not rename an automation or return an owner to `Task[...]` unless the user direction or verified role change requires it.
- To apply a title, identify the existing thread, actual role, and original date; choose the title; use a tool that changes that same thread; then read the same thread and verify the saved title. Retry a temporary race only on that thread. If no title tool is available, report the thread ID, desired title, and missing tool without claiming the rename succeeded.
- Do not create, archive, hand off, move, or choose a host for a thread merely to apply a title. A temporary helper without a visible thread does not need this title.
